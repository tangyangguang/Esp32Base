公共 Web UI 模板基线总览

把已确认的页面能力模板收束为一套可落地的 ESP32 Web UI 基线。

第一版基线

一、总判断

方向成立按页面能力分类，而不是按业务功能分类，能覆盖更多项目，也不会被某个未定稿业务绑住。
第一批足够完整基础壳层、状态、列表、配置、操作、确认、横向状态已经覆盖高频页面。
实现要克制首版应沉淀轻量 CSS、HTML 结构约定和少量 helper，不做重型前端框架。

二、模板清单

当前确认状态
模板定位关键规则状态优先级
基础壳层所有页面共享的顶部、导航、标题、容器、控件密度。三段式紧凑顶部；状态点替代品牌图标；1180px 宽度；32-34px 控件。已认可第一批
状态概览设备首页或任何需要判断当前状态的区域。首行回答是否正常；指标不超过 4 个；异常优先；主操作克制。已认可第一批
列表记录历史记录、事件、对象列表等多条数据展示。紧凑筛选、表头、分页 footer、首页/尾页/跳页、总条数/总页数。已认可第一批
配置编辑业务配置、通道配置、计划配置、低频参数。列表先行；简单字段行内展开；多字段对象独立编辑；每项一句说明。已认可第一批
操作命令开始、停止、跳过、测试、立即执行等一次性动作。命令不是配置；执行中禁止重复开始；拒绝执行说明原因；高风险进确认。已认可第一批
确认保护不可逆或高风险操作前的安全门。独立确认页；影响范围；一次性 token；服务端二次校验；POST 后跳转。已认可第一批
横向状态所有页面共享的成功、失败、空数据、未配置、受限状态。短提示和大空态分工；状态必须可行动；错误原因可读；PRG 结果统一显示。已认可第一批
流程向导校准、首次设置、复杂维护等多步骤任务。依据、实测、核对、保存；首版提供结构模板，不强加给每个项目。已认可第一批
诊断维护系统信息、只读诊断、维护入口、长任务状态和受控原始片段。只读优先；危险动作进确认；限制原始数据长度；不做复杂调试平台。已认可第一批

三、全局硬规则

PRG页面表单和命令提交统一 POST -> 303 -> GET，刷新不能重复提交。
轻量首版不引入前端框架，不做复杂主题系统，不依赖大型 JS。
紧凑PC 不拉散，手机不拥挤；按钮、输入框、section 间距统一。
可行动空状态、错误、拒绝、受限状态都必须告诉用户下一步。

四、业务页面如何组合

不是按业务分类
常见组合页由哪些模板组成说明
设备首页基础壳层 + 状态概览 + 操作命令入口 + 横向状态首页不是一个独立模板，而是状态能力的组合。
设备记录页基础壳层 + 列表记录 + 横向状态无记录、筛选无结果、时间未同步都走横向状态。
设备配置页基础壳层 + 配置编辑 + 确认保护 + 横向状态简单字段行内改，复杂对象进独立编辑页。
设备操作页基础壳层 + 操作命令 + 确认保护 + 横向状态一次性动作与长期配置分离。
校准/首次设置基础壳层 + 流程向导 + 确认保护 + 横向状态首版提供结构；业务项目按需启用。
诊断维护页基础壳层 + 诊断维护 + 操作命令 + 确认保护 + 横向状态长任务和原始片段作为受控状态，不单独做页面类型。

五、建议实现顺序

1CSS 基线变量、容器、导航、section、按钮、表单、tag、notice。
2页面结构 helperheader、nav、title、section、row、actions 等轻量输出函数。
3核心模板状态、列表、配置、操作、确认、反馈、向导、维护。
4示例页用最小示例覆盖首页、记录、配置、操作、向导和维护。
5接入验证优先用灌溉项目验证，再回看风扇和接水优化空间。

六、当前不建议做

不先做完整主题系统可以保留 CSS 变量，但不要为皮肤切换增加复杂度。
不先重做所有业务页先形成模板和示例，再挑痛点最高的灌溉页面接入验证。
不做复杂调试平台诊断维护进入首版，但原始数据只作为受控片段，长任务只作为状态变体。

七、下一步建议

这套基线已经可以进入正式设计文档阶段。我的建议是先写一份设计文档，冻结模板分类、规则、资源边界和实现顺序；你确认后，再进入实现计划。这样不会一边写代码一边继续改方向。
