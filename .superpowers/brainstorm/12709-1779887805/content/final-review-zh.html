公共 Web UI 模板最终总审

把已确认页面能力和首版实现边界合到一页，作为进入实现计划前的最后复核。

能力分类

一、专业复核结论

分类是成立的以页面能力分类，比按灌溉、风扇、接水等业务分类更稳，也更适合基础库沉淀。
首批覆盖完整补齐访问控制和统计摘要后，已经覆盖可预见高频页面。
实现边界清楚做轻量 CSS、结构 helper、分页 helper 和 PRG helper，不做重型组件库。
换肤要轻量支持 CSS 变量级皮肤，不做运行时主题系统和复杂图片资产。

二、模板确认矩阵

进入首批实现
模板是否确认首批职责专业审查
基础壳层确认顶部身份、导航、标题、内容容器、密度基线。必须做，所有页面统一感主要来自这里。
访问控制确认登录、权限不足、会话失效、只读受限。内置页面和业务页都会遇到，不能只靠浏览器弹窗或临时文本。
状态概览确认设备当前状态、关键指标、异常摘要、主操作入口。适合作为设备首页能力，不应扩大成大仪表盘。
统计摘要确认累计值、分组汇总、轻量趋势、占比和最近变化。补上状态和记录之间的空档；不用重图表库，用表格、数字和 CSS 条形即可。
列表记录确认筛选、表头、数据行、分页、空状态。分页 helper 应进入基础库，不能只给 CSS。
配置编辑确认配置列表、行内编辑、独立编辑页、说明文字、保存结果。这是当前最大痛点，首批优先级高。
操作命令确认一次性动作、执行条件、执行中、拒绝原因。必须与配置分离，否则页面语义会混乱。
确认保护确认危险动作独立确认、一次性 token、服务端二次校验。不能只靠前端确认框，基础库应给标准路径。
横向状态确认成功、失败、空数据、未配置、受限、时间未同步。这是所有页面的兜底体验，必须统一。
流程向导确认校准、首次设置、复杂维护等多步骤流程。这类能力在嵌入式设备里常见，首版应提供结构模板，但不是每个项目都必须启用。
诊断维护确认只读诊断、系统信息、维护入口、长任务状态、上传导出、受控原始片段。需要进入首版，但必须受控：不做无限日志墙，不做复杂调试平台。

四、实现边界最终建议

基础库应提供CSS 基线、结构 helper、分页 helper、PRG helper、访问控制、统计摘要、流程向导、诊断维护、示例页。
基础库不应提供业务组件、大型前端框架、运行时主题系统、图表框架、业务数据模型。
业务项目负责具体字段、具体数据、权限规则、业务操作含义和设备状态判断。

五、皮肤和视觉判断

默认风格中性灰底、白色内容面、低饱和主色、明确语义色。简洁、大方，适合设备管理页。
换肤方式用 CSS 变量覆盖主色、背景、边框和语义色。业务可选择主题文件或根 class。
不做什么不做图片皮肤、不做大量渐变、不做运行时主题编辑器，避免占用 ESP32 资源。

六、进入实现计划的顺序

1CSS 基线变量、布局、控件、表格、提示和响应式规则。
2结构 helperpage、nav、title、section、row、actions、notice。
3行为 helperpagination 和 PRG，解决分页重复写和重复提交。
4示例页面首页、统计、记录、配置、操作、向导、维护、访问控制。
5项目验证优先灌溉项目，再评估接水和风扇是否渐进优化。

七、最终判断

这些页面能力已经可以视为第一版确认完成。补齐访问控制和统计摘要后，覆盖面足够；流程向导和诊断维护进入首版；长任务作为操作/维护状态变体处理；原始数据只作为诊断维护中的受控片段，不作为独立模板。
