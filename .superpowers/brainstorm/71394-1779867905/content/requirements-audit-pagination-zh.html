公共 Web UI 需求查漏与分页规范

基于水龙头、风扇、灌溉和 FarmAuto 重新梳理：公共样式库既要服务基础内置页，也要服务业务自定义页。

新增重点：列表分页作为基础模板

一、从现有项目复核出的高频页面

水龙头总览、预设、滤芯配置、出水记录、统计、记录校准。记录页已有分页和每页条数。
风扇运行控制、历史、配置、红外学习。页面内 JS 较多，适合沉淀紧凑控制台和配置模板。
灌溉总览、手动、近期计划、计划配置、记录、设置、调试。计划和每路配置需要紧凑业务配置页。
FarmAuto自动门与喂食器都有业务记录、校准、诊断、计划、料桶和危险确认页。分页、确认、维护态是刚需。

二、公共页面类型目录

这些不是一次全部实现的功能，而是样式库要预留的模板能力，避免后续每个项目重新调页面结构。

页面类型适用场景推荐形态是否当前已遇到
运行总览页设备当前状态、关键指标、下一步动作状态条 + 操作表 + 少量指标已遇到
紧凑业务配置页计划、通道、滤芯、料桶、一路信息单项列表，每项有值、说明和修改入口已遇到
单项编辑页多个字段、会影响业务行为的配置独立 GET 编辑页，POST 后 303 返回已遇到
页面内展开编辑只改一个简单字段当前行展开，保存后回到 GET 展示态已遇到
记录列表页出水记录、灌溉记录、喂食记录、自动门事件筛选条 + 分页列表 + 导出入口需要补强
危险操作确认页恢复出厂、清故障、端点校准、重置计数明确影响、确认文本或 token、POST 后跳转已遇到
校准向导页流量计校准、电流零点、门行程、投喂克数换算分步骤检查，保存前展示核对摘要应纳入
故障处理页位置不可信、水流异常、堵转、传感器异常故障原因、现场处理提示、解除入口、相关记录应纳入
诊断页业务自检、记录索引检查、传感器读数、存储状态只读诊断为主，耗时检查转任务状态已遇到
长任务进度页导出、索引修复、OTA、文件检查命令启动后轮询状态，禁止重复启动未来会遇到
空状态和首次设置页无记录、未校准、未配置计划、时间未同步说明当前缺什么，提供一个主要入口应纳入
原始数据页API JSON、调试快照、日志片段低装饰、可复制、限制输出量未来会遇到

三、公共页面必须遵守的规则

信息密度优先PC 端不要用大片空白堆卡片。状态、说明、操作应该在同一视线范围内完成。
移动端先保证可操作按钮和表单控件要够大，复杂表格在手机上转成条目，不强迫横向滚动。
业务说明放在项内每个业务配置项保留一句必要说明，避免用户改参数时不知道影响范围。
表单统一 PRG页面表单必须 POST -> 303 -> GET，刷新不能重复提交，成功和失败都回展示页。
危险操作二次确认危险动作不能只靠按钮颜色，必须明确影响，必要时输入确认文本或消费 token。
资源消耗有上限CSS 小而稳定，少 JS，少图片；记录查询和导出不能阻塞主循环或一次性全量输出。

六、后端分页规则

推荐默认长期记录使用 `start/limit/nextIndex` 游标式分页。它更适合文件、环形记录和总数计算昂贵的场景。
可选模式当总数和随机页读取很便宜时，可以使用 `page/pageSize/total`，例如已经有索引的水龙头记录页。
每页上限限制每页条数，建议 20、50、100、200，禁止“全部”。服务端必须 clamp，不信任前端。
筛选保持翻页时保留时间、类型、通道、故障原因等 query 参数。修改筛选后回到第一页或 `start=0`。
空状态无记录时显示“当前筛选无结果”，提供清除筛选按钮，不显示空表格。
导出策略导出是单独入口，按当前筛选流式或分块输出，不通过把 `limit` 调大来导出全部。

七、我的专业建议

设计基线采用“紧凑设备工作台 + 紧凑业务配置列表 + 记录分页模板”。它能覆盖你现在最痛的业务页面，同时不把基础库做成重型前端框架。
第一批必须做基础布局、状态条、紧凑配置列表、单项/独立编辑、PRG 表单、分页列表、确认页。
第二批再做校准向导、故障处理页、诊断页、长任务进度页、空状态和导出页。
不要提前做重完整主题系统、复杂图表、大量动画、前端路由框架都不适合当前 ESP32 资源目标。
