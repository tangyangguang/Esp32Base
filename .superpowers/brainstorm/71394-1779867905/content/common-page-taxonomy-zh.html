公共 Web UI 页面体系

这版不按某个未定稿业务项目枚举页面，而是抽象 ESP32 设备 Web UI 的高频共性页面。灌溉项目作为当前优先验证场景。

原则：共性优先，业务举例只作验证

一、页面分层

基础必备每个设备都应有：运行总览、业务配置、记录列表、编辑表单、提交结果反馈。
业务高频多通道、多计划、阈值、维护周期、统计记录这类页面应有统一模板。
按能力启用只有设备涉及计量、传感器、执行器边界时，才启用校准、故障处理、危险确认。
开发维护可选诊断、长任务、原始数据页面向调试和维护，不应挤占普通用户主流程。

二、推荐页面目录

这里的“必须”指公共样式库应该优先提供模板，不等于每个业务项目都必须打开所有页面。

页面类型定位典型内容灌溉项目映射模板优先级
运行总览页用户进来先看设备是否正常、正在做什么、下一步是什么。状态条、关键指标、下一计划、主操作、异常提示。灌溉首页：阀门状态、今日计划、水量、下一次浇水。必须
手动控制页低频但关键的人工执行入口。选择对象、执行模式、时长/目标量、开始/停止、确认。手动浇水：选择一路或多路、时长、开始/停止。必须
紧凑业务配置页查看和修改一组业务对象。对象列表、当前值、必要说明、单项修改入口。一路信息、计划列表、阀门/流量参数。必须
独立编辑页修改多个字段或有业务影响的配置。分组表单、范围提示、保存前核对、返回入口。计划编辑、一路配置编辑。必须
记录列表页查历史、定位问题、查看统计来源。筛选、表头、分页、导出入口、空状态。浇水记录、事件记录。必须
危险确认页保护不可逆或高风险动作。影响范围、当前状态、确认文本/token、POST 后跳转。恢复出厂、清异常、跳过计划、重置计数。按需
空状态/首次设置页设备刚开始使用或某类数据为空时给出明确下一步。没有计划、没有记录、未校准、时间未同步。首次没有计划时，引导创建第一条计划。必须
故障处理页设备处于异常或不可继续状态时，指导用户处理。故障原因、影响范围、处理步骤、解除/复位入口。水流异常、阀门未关闭、时间无效导致计划暂停。按需
校准向导页把“依据、实测、计算、核对、保存”做成流程。流量计、传感器、执行器边界、称重/计量。流量校准如果项目启用，则使用该模板。按需
诊断/维护页给开发者或维护者看系统和业务健康信息。传感器读数、存储状态、最近错误、只读检查。调试页、传感器状态、记录索引检查。可选
长任务页处理导出、修复、扫描、升级等耗时任务。启动任务、进度、结果、禁止重复启动。大量记录导出或索引修复，首版可不做。可选
原始数据页查看 JSON、日志片段或调试快照。低样式、可复制、限制输出量。调试 API 展示，面向开发维护。可选

四、不要被业务例子绑架

FarmAuto、风扇、水龙头都只用来验证模板是否覆盖典型场景；未确认的业务页面不作为公共库的硬需求来源。
多路设备抽象为“通道/一路配置”，可用于灌溉、投喂、多继电器。
共性
计划执行抽象为“计划列表 + 计划编辑 + 跳过/恢复”。
共性
计量校准抽象为“依据 + 实测 + 核对 + 保存”，不绑定水流或投喂。
共性
故障处理抽象为“异常状态 + 处理建议 + 解除入口”，不绑定某个具体机械结构。
共性

五、专业建议

第一阶段先定稿总览页、手动控制页、紧凑业务配置页、独立编辑页、记录分页页、危险确认页、空状态。
第二阶段按需定稿故障处理页、校准向导页。它们要按设备能力开启，不要强加给每个项目。
第三阶段再考虑诊断/维护页、长任务页、原始数据页。优先保证普通业务页面稳定好用。
