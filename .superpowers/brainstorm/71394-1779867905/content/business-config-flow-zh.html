业务配置页与保存前核对

App Config 保持现状；新增的是业务页面里的轻量配置模式，避免每个项目重复写一套复杂表单逻辑。

目标：业务页少写样式，少写重复交互

一、业务配置页不是 App Config 的复制品

二、推荐的业务配置流程

1列表展示先展示当前值、状态、影响范围。用户不用进入表单也能看懂配置。
2单项编辑点击某一项，只编辑一个业务对象或一小组强相关字段。
3保存前核对前端显示 old/new 差异，尤其是危险、校准、会影响运行的修改。
4服务端校验保存最终事实仍由业务 handler 校验；核对页面只帮助用户避免误操作。

业务代码只保留业务事实

校验、权限、保存、运行中拒绝仍在业务 handler。

页面端： - 基础库样式负责布局 - 通用 JS 负责 old/new 核对 - 表单仍提交到业务 POST 路由 业务端： - 重新解析 POST 参数 - 校验范围和业务状态 - 运行中/忙碌时拒绝 - 保存后 303 跳转 - 记录业务事件
不做什么不把业务配置都塞进 App Config；不让基础库理解业务对象；不让前端核对代替后端校验。
基础库做什么提供 CSS class、确认框样式、字段 old/new 标记规则、按钮状态和少量通用 JS。
业务做什么负责字段含义、数据读取、业务校验、保存路径、事件记录和是否允许修改。

四、为什么这种方式不会别扭

App Config继续作为基础库内置低频参数页，保持现有体验。
业务配置用“对象列表 + 单项编辑”，更像产品页面，而不是系统参数页。
共同部分两者共享视觉 token、表单控件、按钮、状态提示和确认体验。
