## 2. 本轮新发现的问题（5 项，全部轻微）

### N1 (轻微) —— Web 配置页回显密码 与 Log 安全策略 在文档里需要互相解释

矛盾点：

- 04_web §7 / 04_web §9：WiFi 配置页**必须回显当前密码**。
- 03_api §3.3 / 10_known §10：日志在 `INFO` 及以下**不输出明文密码**。

读者可能困惑：为什么日志严格而 Web 页面"放任"？

实际是两个独立场景：
- 日志会打到串口/sink/可能被旁观；
- Web 页面在 Basic Auth 保护下用户主动访问、用于运维查看当前配置。

**建议**：在 `10_known_limitations.md §1 安全边界` 增加一行：

> Web 配置页面在用户通过 Basic Auth 后会回显当前 WiFi 密码，这是运维查看当前配置所需。该回显与日志的 INFO 级密码屏蔽策略分别考虑。生产固件应避免在公共网络环境下打开配置页。

修订量：1 行。

### N2 (轻微) —— 02_profiles §3 软依赖列表漏 OTA

03_api §10 OTA 类已声明 4 个 EVENT 常量（ota.start/progress/success/failed），意味着 OTA 是 Bus 的软依赖。但 02_profiles §3 软依赖列表只有 WIFI / WEB / HEALTH。

**建议**：在 02 §3 软依赖列表加一行：

> - `OTA` 可不依赖 Bus；未启用 Bus 时不发布 OTA 事件。

修订量：1 行。

### N3 (轻微) —— WiFi `FAILED` 状态的进入条件与恢复路径仍未明文

03_api §7 列了 `FAILED` 枚举，但全文没说：
- 什么条件进入 FAILED？（maxRetries 用尽？底层 WiFi 错误？）
- 用户怎么从 FAILED 恢复？（必须 connect / clearCredentials / 重启？）

当前文档隐含"默认无限重试"（前几次短间隔 + backoff），所以默认配置下 `FAILED` 几乎不会进入。但用户若设置了有限重试就会走到 FAILED。

**建议**：在 03_api §7 "WiFi 凭证和重连策略" 末加：

> 默认无限重试，`FAILED` 状态在默认配置下不出现。仅当应用显式设置有限 maxRetries 且全部用尽，才进入 `FAILED`。从 `FAILED` 恢复必须通过 `connect()` 重新提交凭证或 `clearCredentials() + startConfigPortal()`。

修订量：3 行。

### N4 (轻微) —— "已保存凭证连接失败时不进入 AP" 是反直觉的设计取舍，应有理由说明

03_api §7 + 04 §9 + 09 §6 + 10_known §3 都写了"有已保存凭证但连接失败时不自动进入 AP/config portal"。

这是有意识的设计：避免量产设备在路由器临时故障时被陌生人接入 AP 改凭证。但**消费级用户搬家/换路由器时会困惑**——设备永远连不上、永远收不到 AP。

**建议**：在 10_known §3 网络边界 已写了这条事实，但应补充**理由 + 应用层应对**：

> 这是为防止量产设备在路由器临时故障时被陌生人通过 AP 改凭证。如果应用面向消费场景需要"换路由器自动配网"，应自行在长 backoff 后调用 `Esp32BaseWiFi::startConfigPortal()`，并配合用户层提示（按键长按、状态灯等）。

修订量：3 行。

### N5 (轻微) —— 06 §2 与 02 §12 裁剪验收表重复

V1 评审已提，V2 仍保留。02 §12 简短列项；06 §2 是详细表格。当前两处不冲突但维护时容易遗漏同步。

**建议**（二选一）：
- (A) 02 §12 改为指向 "详见 06 §2"
- (B) 保持现状，但添加交叉引用注释

修订量：1 行。

## 3. 小幅再核查的几处细节

### 已正确处理但值得复述

- **NTP 对时成功日志**（03_api §8 + 07 §5）：包含实际日期时间 + uptime + 推算 boot wall time。这一条**对量产设备的事后日志分析意义巨大**，超出 V1 评审建议，是亮点。
- **`formatBytes` 二进制单位约定**（03_api §3.3 + 06 §4 + 04 §7）：`1 KB = 1024 bytes` 显式写明，避免与运营商/SI 单位混淆。
- **WiFi 配置页空 SSID/空密码拒绝**（04 §7 + 07 §4 + 09 §6）：前后端双重校验，正确做法。
- **重启按钮二次确认**（04 §7 + 09 §10）：避免误触。
- **`ESP32BASE_BUS_STRICT_TASK_CHECK` 命名**（03_api §6）：正确避开了与 `STRICT_OPTIONAL_BEGIN` 重名。

### 仍可推迟到 Phase 0 之后再写明的几处（可接受）

- **08 §11 brownout 寄存器名称**："实现阶段需要在 Core 2.x / 3.x 分别确认 brownout register 名称和 restore 方式，确认结果写入本文件后才能冻结发布"——这种"先做实验再回填文档"的契约式条款是合理的，**Phase 0 完成后回填**即可。
- **资源记录表全空**（06 §7）："Phase 0 允许先填写裁剪和固件体积字段；Phase 1 起必须补齐"——已声明渐进填表规则，可接受。

## 8. 与 V1 评审版相比的"超额完成"清单

V2 文档**主动补充**了以下 V1 评审未提的内容，工程纪律值得肯定：

1. **NTP 对时成功日志包含 boot wall time** —— 量产事后排障神器。
2. **字节数 raw + KB/MB 二进制单位约定** —— 避免单位混乱的横切要求。
3. **WiFi 配置页空字段双重校验 + 重启二次确认** —— UX 量产打磨。
4. **OTA 上传页进度显示协议**（百分比 + raw + KB/MB）—— 用户可见性。
5. **08 §10 ESP32-S3 USB-CDC 单独成章**——比"加一行"更彻底。
6. **08 §11 brownout 寄存器隔离 + "不支持组合编译失败或降级 warn，不允许静默假装成功"** ——拒绝静默 bug 的工程态度。
7. **07 §2.6 Config / Fs 语义原型** —— 把 deferred 读语义和 Fs 全套 API 列入 Phase 0 原型，比 V1 评审建议更彻底。
8. **07 §8 维护回归章节** —— 明确写出每次维护发布必须重测的最小集。
9. **10_known §11 发布后演进边界** —— 把 09 §12 的精神提炼进 known limitations。
10. **README §快速开始 + setHostname 提示** —— 比 V1 建议的 "5 分钟上手"更精准。
